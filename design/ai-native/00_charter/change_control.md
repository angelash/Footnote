# 变更控制流程 (Change Control Process)

> **文档性质**：变更管理规范（冻结）  
> **版本**: v1.0  
> **创建日期**: 2025-12-29  
> **适用范围**: 所有对冻结文档/范围/系统边界的变更

---

## 1. 变更分类

### 1.1 变更类型定义

| 类型 | 定义 | 示例 | 审批层级 |
|------|------|------|---------|
| **范围变更** | 增减功能/内容 | 新增章节、删除角色 | L0 |
| **技术变更** | 架构/依赖/Schema变更 | 新增npm包、修改存档格式 | L0 |
| **资源变更** | 时间/人力/预算调整 | 里程碑延期、增加预算 | L0 |
| **规格变更** | Spec级别修改 | 事件参数调整、UI状态增减 | L1 |
| **实现变更** | 实现细节调整 | 代码重构、性能优化 | L2 |

### 1.2 变更影响等级

| 等级 | 影响范围 | 示例 | 审批流程 |
|------|---------|------|---------|
| **Critical** | 影响项目目标/里程碑 | 砍掉一个结局 | 完整CR流程 |
| **High** | 影响多模块/多系统 | 修改存档格式 | 完整CR流程 |
| **Medium** | 影响单模块 | 修改UI组件接口 | 简化CR流程 |
| **Low** | 局部实现调整 | 优化算法 | L2 Review |

## 2. CR 申请流程

### 2.1 完整 CR 流程（Critical/High）

```
┌─────────────────────────────────────────────────────────────────┐
│                         CR 完整流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 申请 ─────────────────────────────────────────────────────→ │
│     │                                                           │
│     ▼                                                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ CR Issue 创建                                            │   │
│  │ - 使用 .github/ISSUE_TEMPLATE/change_request.yml         │   │
│  │ - 填写背景、变更内容、影响范围、风险等级                    │   │
│  └─────────────────────────────────────────────────────────┘   │
│     │                                                           │
│     ▼                                                           │
│  2. 评估 ─────────────────────────────────────────────────────→ │
│     │                                                           │
│     ▼                                                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ L1 影响评估                                               │   │
│  │ - 技术总监：技术可行性                                     │   │
│  │ - 策划总监：设计影响                                       │   │
│  │ - QA总监：测试影响                                         │   │
│  │ - PMO：排期影响                                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│     │                                                           │
│     ▼                                                           │
│  3. 审批 ─────────────────────────────────────────────────────→ │
│     │                                                           │
│     ├─── 通过 ──→ 4. 执行                                       │
│     │              │                                            │
│     │              ▼                                            │
│     │         ┌──────────────────────────────────────┐         │
│     │         │ 创建执行 Task Pack                    │         │
│     │         │ 更新相关文档                          │         │
│     │         │ 记录到 decisions_log.md              │         │
│     │         └──────────────────────────────────────┘         │
│     │                                                           │
│     └─── 拒绝 ──→ 5. 关闭                                       │
│                    │                                            │
│                    ▼                                            │
│               记录拒绝原因                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 简化 CR 流程（Medium）

```
申请 → L1 快速评估(24h内) → 通过/拒绝 → 执行/关闭
```

### 2.3 直接 Review（Low）

```
提交 PR → L2 Review → 合并/修改
```


## 4. 审批权限

### 4.1 审批矩阵

| 变更类型 | L0 | L1 | L2 | 时限 |
|---------|:--:|:--:|:--:|------|
| 范围变更 | ✅ | 评估 | - | 48h |
| 技术变更 | ✅ | 评估 | - | 48h |
| 资源变更 | ✅ | 评估 | - | 24h |
| 规格变更 | 知悉 | ✅ | 评估 | 24h |
| 实现变更 | - | 知悉 | ✅ | 4h |

### 4.2 审批条件

**通过条件**（全部满足）：
- [ ] 变更必要性已论证
- [ ] 影响范围已评估
- [ ] 回滚方案已准备
- [ ] 相关方已知悉
- [ ] 排期可承受

**拒绝条件**（任一满足）：
- 违反项目宪法
- 影响里程碑且无缓解
- 技术风险不可控
- 资源超出预算

## 5. 回滚策略

### 5.1 回滚分类

| 回滚类型 | 触发条件 | 执行方式 | 时限 |
|---------|---------|---------|------|
| **即时回滚** | Blocker缺陷 | Git revert | 1h内 |
| **计划回滚** | 方案失败 | 按回滚方案执行 | 24h内 |
| **部分回滚** | 部分功能问题 | 选择性revert | 按评估 |

### 5.2 回滚检查清单

执行回滚前必须确认：

- [ ] 已备份当前状态
- [ ] 已通知相关方
- [ ] 已准备回滚脚本/命令
- [ ] 已准备验证方案

### 5.3 回滚记录

每次回滚必须记录到 `docs/05_logs/rollback_log.md`:

```markdown
## ROLLBACK-YYYY-NNNN

- **时间**: YYYY-MM-DD HH:MM
- **触发原因**: 
- **关联CR**: CR-YYYY-NNNN
- **回滚范围**: 
- **回滚方式**: [Git revert / 手动修改 / 脚本执行]
- **执行人**: 
- **验证结果**: [成功/部分成功/失败]
- **后续措施**: 
```

## 6. 紧急变更流程

### 6.1 定义

**紧急变更**: 影响线上运行、必须在 4 小时内处理的变更。

### 6.2 流程

```
1. 口头通知 L0/L1
2. 直接执行修复
3. 24小时内补充 CR Issue
4. 48小时内完成 Post-mortem
```

### 6.3 Post-mortem 模板

```markdown
## 紧急变更复盘 - ECR-YYYY-NNNN

### 基本信息
- **发生时间**: 
- **发现人**: 
- **处理人**: 
- **恢复时间**: 

### 问题描述
<!-- 发生了什么？ -->

### 影响范围
<!-- 影响了什么？ -->

### 根因分析
<!-- 为什么会发生？ -->

### 修复措施
<!-- 做了什么修复？ -->

### 预防措施
<!-- 如何防止再次发生？ -->

### 流程改进
<!-- 流程上需要改进什么？ -->
```

## 7. 常见场景指南

### 7.1 "我想加一个新功能"

```
1. 检查是否在 In-Scope 范围内
2. 如果是 → 创建 Task Pack，正常流程
3. 如果不是 → 创建 CR Issue，走审批流程
```

### 7.2 "我想改存档格式"

```
1. 创建 CR Issue（技术变更，High）
2. 技术总监评估迁移方案
3. L0 审批
4. 创建迁移 Task Pack
5. 实现 + 测试
```

### 7.3 "我想引入新 npm 包"

```
1. 创建 CR Issue（技术变更，Medium）
2. 说明：包名、版本、用途、包体影响
3. 技术总监评估
4. L0 审批
5. 执行
```

### 7.4 "发现线上 Bug 需要紧急修复"

```
1. 口头通知 L0/L1
2. 直接修复（绕过正常流程）
3. 24h 内补充 CR Issue
4. 48h 内 Post-mortem
```

```
                   └──────────┘
```

## 9. 审计与追溯

### 9.1 必须记录

所有 CR 必须记录以下信息：

- CR 编号
- 申请人/时间
- 变更内容摘要
- 审批结果/审批人
- 执行结果
- 相关 Task Pack / PR

### 9.2 记录位置

| 记录类型 | 位置 |
|---------|------|
| CR Issue | GitHub Issues |
| 决策记录 | `docs/05_logs/decisions_log.md` |
| 回滚记录 | `docs/05_logs/rollback_log.md` |
| 任务记录 | `docs/05_logs/task_log.md` |
